What2Eat 验收课 · 约 35–50 分钟

你不是在“点一点”，而是在收集发布证据

这节课的目标，是让你独立回答一个二元问题：当前 commit 是否可以作为 v1 发布？ 最终证据来自自动化、真实浏览器旅程、真机、持久化和恢复演练五个层面。

自动化证明

已编码的规则没有回归，主流桌面与移动视口能跑通。

手工证明

真实 NIM、真实触控、文案和完整用户心智链路可用。

恢复证明

容器可替换、卷可复用，备份真的能恢复，而不只是“文件存在”。

1. 建立隔离的验收环境

使用独立 Compose project，避免碰到现有数据。Docker 的命名卷会在后续启动中复用； up --wait 会等待服务进入 running/healthy 状态，依据见 Docker Compose up 和 volumes 参考。 

git pull --ff-only
install -m 600 .env.example .env.acceptance
openssl rand -base64 32

# 编辑 .env.acceptance：填入真实 NVIDIA_API_KEY，并把生成值填入 SESSION_SECRET
docker compose --env-file .env.acceptance -p what2eat_acceptance up --build -d --wait
docker compose --env-file .env.acceptance -p what2eat_acceptance ps
curl -fsS http://127.0.0.1:8080/api/healthz
停下来检查：不要把终端里的秘密、.env.acceptance 或数据库备份截图上传到 issue。 如果 8080 被占用，先停止占用者；不要随手改正式 Compose 配置来“通过验收”。

2. 先跑自动化门禁

go test ./...
go vet ./...

cd frontend
npm run typecheck
npm run test:browser
cd ..

四条命令都应以退出码 0 结束。浏览器测试使用仓库的可控测试服务，不消费真实 NIM 配额；它证明已写入测试的行为，不证明真实密钥、真实网络或真机触控正常。

3. 完成真实桌面旅程

  1. 用全新用户名注册，确认进入 Onboarding，而不是空白页或登录页。
  2. 在访谈中明确提到 Catalog 里的菜，例如“番茄牛肉蛋花汤”和“番茄红酱”，确认建议来自服务端真实 NIM 调用，且可加入 Candidate pool。
  3. 在 Candidate pool 搜索、添加、删除一道菜，并调整权重；刷新页面后状态仍在。
  4. 保持一个很小的池（1–2 道），开始 Meal，执行一次 Reroll，再 Accept；确认 Recipe 可阅读。
  5. 继续下一顿，观察小池/冷却压力下的 Discovery 标识和推荐理由；接受后进入下一顿并提交 Pending rating。
  6. 退出后重新登录，确认 Candidate pool、Meal、rating 状态仍可访问。
NIM 的聊天接口与 OpenAI Chat Completions 兼容，真实验收要证明请求确实穿过 Go 服务，而不是只证明前端页面能打开。接口语义可对照 NVIDIA NIM API 参考。

4. 检查 Cookie 与真机

在浏览器 Network 面板查看注册或登录响应，确认会话 Cookie 带 Secure、HttpOnly 和 SameSite=Lax。 Secure Cookie 除 localhost 特例外只通过 HTTPS 发送，所以局域网 http://192.168… 不是有效的正式真机验收入口。依据见 MDN Set-Cookie。

  • 先用 Chrome Device Mode 的 390×844 视口预检：无横向滚动、主按钮可见、软键盘不遮住当前输入。
  • 再用至少一台实际手机，通过 HTTPS URL 完成注册、Onboarding、选菜、Reroll、Accept 和 Rating。
  • 旋转屏幕一次，并检查长菜名、Recipe、错误提示和加载状态。

Device Mode 官方也将其定位为移动体验的近似模拟，因此它不能替代真机： Chrome Device Mode。

5. 证明容器可替换、数据不可丢

在已经创建账户和 Meal 状态之后执行：

docker compose --env-file .env.acceptance -p what2eat_acceptance \
  up -d --force-recreate --wait app

重新登录，逐项确认账户、Candidate pool、Meal、Pending rating 与 Taste rating 仍在。失败意味着“容器重建不丢数据”未达到验收条件，应保存 docker compose ... logs app 后停止发布。

6. 做一次真的备份与恢复

严格按仓库 README 的“备份与恢复” 操作：把每次 Compose 调用改为 docker compose --env-file .env.acceptance -p what2eat_acceptance …， 把命令中的 .env 文件名替换为 .env.acceptance，并使用新的带日期 备份目录。备份后先改变一项容易识别的状态，再恢复数据库和配套 env。

恢复通过的证据不是“命令没报错”，而是：

  • 原 Account 可以登录；
  • 恢复前快照中的 Candidate pool、Meal 和 rating 都存在；
  • 备份后故意增加的那项状态消失，证明读取的是恢复快照；
  • 应用日志没有 SQLite 权限或 session 解密错误。
数据库和当时的 SESSION_SECRET 必须成对保管。恢复演练不要使用 down -v；它会删除命名卷。

7. 做发布判断

打开并打印（或直接在浏览器勾选） v1 验收清单。 所有必选项通过，且没有 P0/P1 缺陷时，才建议关闭 #11 和 v1 父 issue，并打 v0.1.0 标签。

你的练习：亲自完成清单，在每个分区至少留一条证据（命令结果摘要、URL、 非敏感截图或日志时间点）。把结果发给我，我会检查证据是否足够，但不替你勾选。

8. 清理隔离环境

docker compose --env-file .env.acceptance -p what2eat_acceptance down -v

这会删除名为 what2eat_acceptance 的验收容器、网络和卷；请先确认备份演练 已结束，而且没有把正式数据放进这个 project。保留的备份目录仍需按敏感数据处理。
